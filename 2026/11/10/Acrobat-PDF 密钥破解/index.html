Acrobat-PDF 密钥破解

Created2026-11-10|Updated2026-11-10
|Word Count:6.8k|Reading Time:22mins|Post Views:|Comments:

从 15 份 PDF 开始

这次整理英语六级试卷时，我希望文件既能在 PDF 编辑器中修改，也能搜索、复制其中的文字。目录里共有 15 份 PDF、110 页，检查后发现，它们其实有两种问题：14 份设置了编辑权限限制；另 1 份没有加密，却在提取文字时出现了乱码。

处理完成后，14 份文件移除了加密和编辑限制，另 1 份恢复了文字映射并补上标题搜索文字。全部 110 页都做了处理前后的渲染比对，页面显示一致。

文章沿用“密钥破解”这个标题，但本次主流程实际是使用空用户密码解密、另存无加密副本，再修复搜索文字，没有穷举未知密钥，也没有找回所有者密码。实际操作使用 Python，Acrobat 图形界面的方法放在后面的拓展部分。

本文面向自己持有或已获授权处理的文件。解除编辑限制、恢复搜索能力和恢复遗忘的密码，需要分别判断，不能只看一个“解锁成功”的提示。

先分清密码、权限和密钥

能直接打开，不代表文件没有加密

PDF 的用户密码和所有者密码可以用于取得文档解密所需的信息。常见的“直接打开，却不能编辑”场景，是用户密码为空、所有者密码非空，阅读器使用空密码打开后，再执行文件声明的权限限制。qpdf 的官方文档专门解释了这种情况。[^1]

概念影响什么本次遇到的情况
用户密码，常称打开密码能否解密并打开文档14 份加密文件的空用户密码均有效
所有者密码，常称权限密码阅读器对编辑、打印等操作的限制原文件限制编辑；本次没有恢复这个密码
加密密钥底层加解密使用的数据本次没有暴力搜索或输出密钥
文字映射字符编码能否还原成正确文字另 1 份需要单独修复

密码和加密密钥也不是同一个东西。对于本文涉及的标准密码安全处理器，密码参与获得文档密钥；已经能用有效密码解密时，可以重新写出不带加密的文档。[^1]

可以显示，也不代表可以搜索

本次特殊文件使用 Type 3 自定义字形，缺少可用的 /ToUnicode 映射。渲染器仍然能画出字形，提取器却不能可靠地知道这些字形对应哪个字符。Type 3 字体本身并不等于乱码，问题在于这份样本的文字编码与映射。

/ToUnicode 可以理解为“字符代码到 Unicode 文字的对照表”。补回正确映射后，搜索和复制才有机会恢复；已经变成路径轮廓的文字没有字符代码，需要另补文字层。[^2]

本次怎样恢复 355 个字形

这部分采用了针对样本的处理，不能把映射表直接套到其他 PDF：

  1. 将 8 页渲染为 200 DPI 图片，分别用 Windows 的英文、简体中文 OCR 取得词和词框。
  2. 读取字体的 /Encoding、/CharProcs，按字形流的 SHA-256 合并重复形状。
  3. 结合字形自身的路径范围和逐字符坐标，把字形中心与 OCR 词框对齐。
  4. 对字形数量与识别文字长度相符的词，建立候选映射；利用重复出现的同一字形投票。
  5. 将字形与映射文字排成校对图，逐项核对。这里修正了 已/己、究/宄 等识别混淆。
  6. 写回 /ToUnicode，保留原字形绘制内容。轮廓标题另补一层不可见文字。

Windows OCR 能返回按行、按词组织的识别结果和位置，适合辅助这种对齐。识别结果仍需要校对，尤其要检查斜体英文、数字和形近汉字。[^4]

本次共校对了 355 个不同字形形状；8 个字体资源的字符映射合计 1035 条。这两个数字统计对象不同，不应写成“355 个字体”。

其中一个排错点是坐标。起初只使用变换矩阵中的平移量，同一个文本对象内的多个字符可能落在相同位置。改用 FPDFText_GetCharOrigin 的逐字符原点后，再结合矩阵的缩放和字形路径范围，对齐才恢复正常。这里的 API 作用可查 PDFium 官方头文件，本次现象则来自项目实测。[^5]

拓展：其他密码处理和恢复方法

这一章区分“知道密码后移除保护”与“遗忘密码后尝试恢复”。Acrobat、qpdf、John 和 Hashcat 的命令或路径已核对官方资料，本次没有在本机运行这些程序；Python 小范围候选方法另用自建加密样本做了实测。

方法适合什么情况是否需要猜测密码本文验证范围
Acrobat 移除保护知道所需密码，希望在界面操作否官方操作路径核对
qpdf 解密空用户密码或已知有效密码否官方参数核对
Python 候选列表有少量自己记得的候选是自建样本实测
John 字典与规则需要批量尝试候选及其变形是官方文档与工具来源核对
Hashcat 字典与掩码有算法信息和密码组成线索是官方模式与语法核对
OCR 或重建文字层能看到页面，但搜索文字缺失否本次特殊样本实测

方法一：在 Acrobat 中移除已知保护

按 Adobe 当前官方文档，在桌面版 Acrobat 中打开目标文件后：

  1. 选择 All tools → Protect a PDF。
  2. 在左侧高级属性区域选择 Set security properties。
  3. 进入 Security 页签，点击 Change Settings。
  4. 按需要取消“打开文档需要密码”或“限制文档编辑和打印”的选项。
  5. 如果提示输入权限密码，输入已知密码，确认并保存副本。

重新打开副本后，检查其安全属性与实际操作。不同界面语言的文字可能不同，以上入口来自 Adobe 官方说明，不是本次机器的点击录像。它需要已知的相应密码，不能恢复遗忘的密码。[^6]

完全穷举需要怎样判断成本

如果每个位置有 C 种可能、长度固定为 L，候选总数是 C^L。例如，6 位纯数字是 10^6 种，10 位大小写字母加数字是 62^10，约为 8.39 × 10^17 种。

估算时间时，可用“候选总数 ÷ 本机对该模式的实际尝试速率”。不要把其他算法或其他显卡的速度套到当前 PDF 上。John 的增量模式文档也提醒，范围过大的完整搜索往往需要人为中止。[^9]

实际恢复时，我会先检查密码管理器、发送记录、原始文档和自己的历史候选，再缩小规则或掩码。未知的长随机密码没有一个可以保证成功的通用恢复命令。

OCR、打印和扫描转换分别能做什么

OCR 可以从已经能看到的页面识别文字，本次就是把它用于修复搜索。它不能读取尚未解密的页面，也不会恢复原始密码。[^4]

“打印为 PDF”得到的是重新生成的文档，不能当成保留原结构的解密流程。对本次还要编辑和搜索的文件，我选择保留原文档对象，再验证显示和文字。扫描或轮廓内容需要额外重建文字；有数字签名的文件则应保留原件，重写后的副本不能视为保持原签名有效。[^7]

还要留意一个提取差异：特殊文件修复后，pypdf 的提取结果曾在字母间插入空格，但 PDFium 的提取和实际搜索可以连续匹配。本次保留了两种检查，没有只靠某个提取器的字符串结果判断搜索是否恢复。PDFium 的渲染、文本和搜索接口见其官方 Python API。[^12]

不应把“再保存一次”当成所有问题的修复。本次最关键的判断，就是先把加密权限问题与文字编码问题分开。

总结

这次处理完成了 15 份 PDF 的权限解除和文字修复，110 页显示与原版一致，也保留了原件备份。整理博客时，配套批处理脚本重新通过了 110 页比较，样本修复又单独比较了 8 页，候选密码方法则通过了自建加密文件实验。

我会把这套流程保留下来：先检查能否打开，再判断加密与权限，随后检查文字层，最后验证输出。能用空用户密码打开的文件，直接解密另存；遗忘的密码，根据实际线索限定候选；文字映射损坏，则进入独立的修复流程。

当前目录不是 Hexo 站点，文章采用标准 Markdown 和本地 PNG，不依赖额外标签插件。迁移时，将 BLOG/_posts 的文章放入 Hexo 的 source/_posts，把 BLOG/images 放入 source/images，保留目录名。文章标题中的空格使用 Markdown 尖括号路径表示，迁移后还应执行目标站点的构建和页面预览。
