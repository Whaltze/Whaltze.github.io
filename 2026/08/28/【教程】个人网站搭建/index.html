【教程】个人网站搭建

Created2026-08-28|Updated2026-08-28
|Word Count:9.7k|Reading Time:31mins|Post Views:|Comments:

本文面向第一次接触网站部署的读者，记录如何从一个本地网页开始，逐步发布到互联网，并解释 GitHub Pages、自定义域名、中国大陆服务器、ICP备案、内网穿透和 IPv6 之间的关系。

信息整理日期：2026 年 7 月 18 日。本文已结合 sore.kdns.fr、DNSHE 与 Cloudflare 的实际配置和排查过程。备案政策、平台功能及云服务商规则可能调整，实际操作时应再次查阅官方文档。

一、网站为什么能被别人打开

一个最基础的网站由三部分组成：

  • 网页文件：HTML、CSS、JavaScript、图片、字体、音频等。
  • 网站托管：一台持续联网、负责把网页文件发送给访客的计算机或平台。
  • 访问地址：可以是域名，也可以是 IP 地址。

这一节先用普通域名讲清规则，再解释本次真实案例。

5.1 子域名作为网站地址

假设：

先进入网站仓库：

DNS 控制台已经知道当前管理的是 example.com，因此“名称”只要求填写相对部分 birthday。它会自动拼接成 birthday.example.com。

不要把目标写成：

DNS 处理的是主机名，不认识 /birthday 这类网页路径。

5.2 根记录为什么写 @

@ 代表“当前 DNS 区域本身”，也叫区域顶点、根记录或 apex。它不是一个真的字符，不会出现在最终网址里。

当前打开的 DNS 区域名称填写最终域名
example.com@example.com
example.comwwwwww.example.com
example.combirthdaybirthday.example.com
sore.kdns.fr@sore.kdns.fr
sore.kdns.frwwwwww.sore.kdns.fr

这正是 sore.kdns.fr 案例中容易困惑的地方：虽然从整个互联网域名结构看，它位于 kdns.fr 下面，但它已被单独委派给 Cloudflare，Cloudflare 当前管理的区域就是 sore.kdns.fr。所以其中的 @ 表示 sore.kdns.fr，而不是 kdns.fr。

如果控制台明确要求完整域名，应按其界面说明填写；多数常见 DNS 控制台使用相对名称。保存后应查看界面显示的完整记录，避免形成 sore.kdns.fr.sore.kdns.fr。

5.3 根域名和子域名的记录类型不同

GitHub 官方给普通独立根域名提供的标准方案是四条 A 记录，也可以使用 DNS 服务商提供的 ALIAS 或 ANAME：

类型名称记录值
A@185.199.108.153
A@185.199.109.153
A@185.199.110.153
A@185.199.111.153

IPv6 的四条 AAAA 记录是可选项，必须使用 GitHub 官方文档当前列出的值，不要从旧教程复制。

对于 blog.example.com、www.example.com 这类子域名，标准做法是 CNAME 到 用户名.github.io。Cloudflare 允许在区域顶点创建 CNAME，并通过 CNAME Flattening 返回最终 IP，因此在 Cloudflare 中给 sore.kdns.fr 的 @ 建立 CNAME 也可以工作；这是 Cloudflare 提供的顶点扁平化能力，不代表传统 DNS 标准原生允许根域名 CNAME。

5.4 www 不是必填项

如果只打算让朋友访问 sore.kdns.fr，只配置这个名称即可。www.sore.kdns.fr 是另一个独立域名，不会自动存在。

若希望两者都能访问，可添加：

类型名称目标
CNAMEwwwwhale.github.io

GitHub 对普通根域名网站建议同时配置 www 变体，并能在正确配置后自动把两者重定向到 Pages 中选定的主域名。但对已经很长的免费子域名，www.sore.kdns.fr 实际价值不大，可以不配。

5.5 Cloudflare 小黄云是否必须关闭

“绑定 GitHub Pages 时必须关闭 Cloudflare 代理”不是 GitHub 写明的绝对规则。更准确的经验是：

  1. 初次绑定、DNS 检查和证书签发阶段，先使用灰云 DNS only 最容易排错。 此时公共 DNS 可以直接看到 GitHub 目标，不会把 Cloudflare 的代理 IP 误当成源站记录。
  2. GitHub 显示 DNS 检查成功，并成功签发自定义域名证书后，再决定是否打开橙云 Proxied。
  3. 开启代理后，访客先连接 Cloudflare，再由 Cloudflare 连接 GitHub Pages；以后排错需要同时考虑两层缓存、证书和重定向。
  4. 若 GitHub 后续又报告 DNS 配置异常，可暂时恢复灰云，确认记录和证书无误后再试。

因此，灰云是稳妥的初始化和诊断方法，而不是所有情况下永久关闭代理的硬性要求。

需要理解的是：更换域名或打开 Cloudflare 代理不会改变 GitHub Pages 这个源站，也不能保证中国大陆访问速度。 Cloudflare 普通全球网络与中国大陆境内 CDN 不是同一个概念，实际效果必须用目标地区和目标运营商测试。

六、中国大陆访问与 ICP 备案

ICP备案主要取决于网站是否使用中国内地服务器提供互联网信息服务，而不是访客是不是中国人。

可以用下面的表格快速判断：

托管位置或方式通常是否需要中国内地 ICP 备案大陆访问情况
GitHub Pages否需要实际测试，不保证稳定
中国香港服务器否通常可访问，但不保证各地质量
日本、新加坡等境外服务器否取决于线路和运营商
中国内地云服务器是完成备案后更适合长期服务
中国内地 CDN通常要求域名已有备案通常较快
国内平台提供的现成公开页面通常无需用户单独备案由平台统一管理，受平台规则限制

工信部现行规定包含通过域名访问和仅通过 IP 地址访问的网站。使用中国内地服务器公开提供网站服务，不能通过改端口、改用 IPv6 或只使用 IP 地址来自动免除备案。

  • 如果增加完全独立的新域名，通常需要把新域名作为新网站或新服务加入备案；
  • 不同省份通信管理局和云服务商可能有不同的数量及材料要求；
  • 备案主体、域名实名认证和服务器账号应保持符合审核规则；
  • 个人网站允许展示的内容范围需要服从所在地管局要求。

ICP 备案和公安联网备案不是同一件事

ICP备案一般通过服务器接入商提交。网站开通后，还应根据所在地要求办理公安联网备案，并在网站底部正确展示相应备案信息。

七、一台服务器可以放多少个网站

技术上，一个公网 IP 可以同时承载多个域名和网站：

Nginx、Caddy、Apache 等软件会读取访客请求中的域名，再决定返回哪个网站。

因此，一台服务器能放多少网站没有统一的技术数字，实际取决于：

  • CPU 和内存；
  • 公网带宽和每月流量；
  • 图片、视频和音频大小；
  • 同时访问人数；
  • 网站是否有数据库和后端程序；
  • 云服务商为该服务器提供的备案网站数量；
  • 自己是否有能力维护更新和安全。

几个低访问量的静态网站通常不会产生很大压力。但是，服务器“技术上能绑定很多域名”不等于“这台服务器拥有无限备案名额”。购买前需要咨询云厂商：该产品是否具有备案资格、能支持多少网站，以及购买期限是否满足备案要求。

九、免费域名和免费小服务器是否可行

可以实现，但很难同时获得以下四项：

境外免费服务器加免费子域名

这种组合通常不需要中国内地 ICP 备案，也可能让大陆用户直接访问，但必须满足：

  1. 服务器拥有可公开访问的网络入口；
  2. 允许开放 HTTP/HTTPS 服务；
  3. 免费子域名支持所需 DNS 记录；
  4. 网站能够配置 HTTPS；
  5. 免费实例不会频繁休眠或被自动回收；
  6. 免费流量和带宽足以承载图片、音乐；
  7. 网页不依赖访问不稳定的第三方字体、视频或脚本；
  8. 在中国移动、联通、电信网络下提前测试。

它适合临时生日页面和学习实验，但不能承诺长期在线。

中国内地免费或试用服务器

服务器免费并不意味着网站免备案。部分免费、试用、按量付费或期限太短的内地云服务器甚至不能作为备案资源，也可能限制 80、443 端口上的未备案网站。

因此，不应把下面的组合当作可靠方案：

国内平台分配的公开页面

如果平台本身提供合法的公开页面、个人主页或网站发布功能，并使用平台自己的网址，用户通常不需要单独购买服务器和办理独立域名备案。

此时平台是服务提供方，用户必须接受平台的内容审核、功能限制、广告、水印和随时调整服务的可能性。不要把“使用平台页面”与“把平台的子域名指向自己的内地服务器”混为一谈。

十、本地部署与内网穿透

内网穿透可以把本机网站临时发布到互联网：

以 Cloudflare Tunnel 为例，本地程序会主动连接 Cloudflare，不要求家庭网络拥有公网 IPv4，也不需要在路由器上开放入站端口。

它适合临时分享和备用入口，但存在明显限制：

  • 本机必须始终开机；
  • 电脑不能睡眠或休眠；
  • 家庭网络断开后网站立即失效；
  • 免费穿透地址可能发生变化；
  • 穿透服务在大陆的连接质量需要测试；
  • 家庭上行带宽可能影响图片和音乐加载；
  • 错误配置可能暴露管理后台或其他本地服务。

安全配置原则：

  • 只把单一网站端口交给穿透程序；
  • 不暴露路由器后台、远程桌面、文件共享和数据库；
  • 不在网页代码中放置密码、密钥和隐私资料；
  • 临时网站使用结束后关闭穿透服务；
  • 如果只给指定朋友访问，应启用访问认证。

内网穿透解决的是连通问题，不应被视为规避备案的办法。

十一、直接使用家庭 IPv6

如果家庭宽带提供全球可路由的 IPv6，可以尝试让朋友直接访问家里的电脑：

要成功，必须同时满足：

  1. 获得的不是以 fe80: 开头的本地链路地址；
  2. 朋友的网络同样支持 IPv6；
  3. 路由器 IPv6 防火墙仅放行网站所需端口；
  4. 电脑防火墙允许对应端口；
  5. 运营商没有限制入站访问；
  6. 网站程序监听 IPv6 地址；
  7. 家庭 IPv6 前缀变化时能自动更新 DNS；
  8. 电脑保持开机联网。

朋友没有 IPv6 时，这个入口完全无法使用。因此，IPv6 不适合作为生日网站的唯一地址。

不要关闭整个 IPv6 防火墙。只应针对运行网站的设备放行必要端口，例如 TCP 443。不要开放远程桌面、文件共享、数据库或路由器管理界面。

直接使用长串 IPv6 地址不方便，也不利于 HTTPS。更合适的方式是给域名添加 AAAA 记录，并使用动态 DNS 更新发生变化的家庭 IPv6 地址。

与内网穿透相同，IPv6 改变了访问路径，但不会自动改变备案规则。

十二、怎样选择最适合自己的方案

临时生日网站

推荐：

提前几天完成以下测试：

  • 手机关闭 Wi-Fi，使用移动网络访问；
  • 让异地朋友分别通过移动、联通、电信测试；
  • 检查图片、字体、音乐和动画是否完整；
  • 检查 HTTPS 是否正常；
  • 准备第二个备用网址；
  • 确认电脑不会自动睡眠。

长期个人博客

如果 GitHub Pages 在目标网络下表现正常，可以继续使用并绑定自定义域名。

如果主要读者位于中国大陆、访问稳定性要求较高，可考虑：

  1. 购买符合备案条件的中国内地云服务器或静态托管；
  2. 为自己的独立域名完成实名认证；
  3. 通过实际接入服务商办理 ICP 备案；
  4. 备案通过后迁移博客；
  5. 配置 HTTPS、自动备份和安全更新；
  6. 根据要求完成公安联网备案并展示备案号。

只分享给一个指定朋友

如果不要求“任何浏览器都能直接打开”，还可以采用带身份验证的私人网络或访问控制。朋友需要登录或安装客户端，但网站不会完全公开暴露在互联网上，安全性通常更高。

十三、常见误区

误区 1：购买域名就等于购买服务器

错误。域名只是地址，服务器或托管平台才保存网站文件。

误区 2：换成自定义域名就能改善 GitHub Pages 的大陆访问

错误。更换域名不会改变源站托管位置。

误区 3：主域名备案后，任何人都可以使用它的子域名搭建内地网站

错误。备案主体、域名所有者和实际接入关系需要符合要求。平台统一托管页面与用户自行接入服务器是两种不同情况。

误区 4：使用 IP、IPv6 或非标准端口就不需要备案

错误。公开网站是否纳入备案管理，不以端口和 IPv4/IPv6 作为简单豁免条件。

误区 5：一台服务器只能运行一个域名

错误。同一台服务器可以根据域名运行多个网站。

误区 6：免费服务器一定适合备案

错误。试用、按量或期限不足的资源可能没有备案资格。

误区 7：网站能打开一次，就代表生日当天一定稳定

错误。应在目标地区、目标运营商和目标设备上多次测试，并准备备用入口。

十四、给小白的最终路线图

第一次做网站时，最重要的目标不是购买最复杂的服务器，而是完成一个小而完整的闭环：

做出网页 → 成功发布 → 让异地朋友打开 → 找出问题 → 逐步升级。

15.4 为什么 0606.cc.cd 会被 Cloudflare 判定为无效域名

有些看起来像普通域名的免费名称，实际上位于平台管理的共享后缀下面。Cloudflare Free 的完整区域接入通常要求它能识别并接受用户有权管理的区域边界。如果 cc.cd 被公共后缀规则或 Cloudflare 的系统视为平台共享后缀，0606.cc.cd 就可能无法像普通注册域名一样添加为独立区域。

这不等于名称一定拼错，也不等于必须先在 DNSHE 添加网站 CNAME。应依次判断：

  1. 名称是否已经真实注册或分配，而不只是控制台中显示“正常”；
  2. 公共 DNS 能否查到它的 NS、SOA 或 TXT；
  3. 提供者是否允许对子域进行 NS 委派；
  4. Cloudflare 是否接受该层级作为独立区域；
  5. 若 Cloudflare 始终拒绝，保留原 DNS，把域名直接 CNAME 到 GitHub Pages 或 Cloudflare Pages，而不要强求完整接管；
  6. 长期项目优先购买自己可续费、可转移、可修改 NS 的普通注册域名。

十七、HTTPS 证书、代理模式和重定向循环

17.1 GitHub 的 HTTPS 为什么暂时不能勾选

保存自定义域名后，GitHub 会先检查 DNS，再排队申请证书。官方说明这个过程可能需要一段时间，Enforce HTTPS 最长可能在 24 小时后才可用。因此不要把“15 分钟到 1 小时”理解成硬性保证。

推荐顺序：

  1. Cloudflare 记录保持灰云；
  2. GitHub Pages 保存自定义域名；
  3. 等待 DNS 检查成功和证书签发；
  4. 勾选 Enforce HTTPS；
  5. 确认 https://sore.kdns.fr 直接访问正常；
  6. 再决定是否开启 Cloudflare 代理。

若长时间没有证书：

  • 检查是否有冲突的 A、AAAA、CNAME、CAA 记录；
  • 确认 CNAME 目标没有仓库路径；
  • 清理旧的自定义域名后重新保存，以重新触发签发任务；
  • 等待公共 DNS 缓存传播，GitHub 提醒最长可能达到 24 小时；
  • 检查页面里的图片、CSS、脚本是否仍使用 http://，避免混合内容。

17.2 开启小黄云后的两段 HTTPS

Cloudflare 的 SSL/TLS 模式决定第二段如何连接源站：

  • Flexible：Cloudflare 到源站使用 HTTP；源站又把 HTTP 重定向到 HTTPS 时，容易形成无限循环。
  • Full：Cloudflare 使用 HTTPS 连接源站，但不严格验证源站证书。
  • Full (strict)：使用 HTTPS，并验证源站证书有效、未过期且名称匹配；在源站证书满足条件时安全性最高。

GitHub Pages 已为正确绑定的自定义域名签发可信证书后，优先使用 Full (strict)。如果源站证书尚未签发就提前打开严格模式，Cloudflare 可能返回 526，而不是帮你自动修好源站证书。

遇到 ERR_TOO_MANY_REDIRECTS 时：

  1. 临时关闭 Cloudflare 代理，判断问题在 GitHub 还是 Cloudflare；
  2. 检查是否仍为 Flexible；
  3. 检查 Cloudflare 的“始终使用 HTTPS”、重定向规则和 GitHub 的强制 HTTPS 是否互相打架；
  4. 清除 Cloudflare 缓存和浏览器缓存后再测；
  5. 不要在多个规则中让 www 与根域名相互反向跳转。

十八、Cloudflare 邮件警告怎么理解

“邮件无法发送到该地址，且可能被伪造”通常表示当前区域没有完整的邮件 DNS 记录，例如 MX、SPF、DKIM 或 DMARC。它与网站 A/CNAME 解析相互独立，不会阻止博客打开。

如果完全不使用 @sore.kdns.fr 邮箱，可以暂时忽略网站面板里的提醒。若要降低别人伪造发件人的可能，可根据邮件服务商指导配置 SPF、DKIM 和 DMARC；不要照抄不属于自己邮件服务的记录。

18.1 Cloudflare Email Routing

Email Routing 更像“邮件转寄规则”，不是传统邮箱：

它适合免费代收。普通配置不会自动提供网页邮箱、IMAP/POP3 或任意 SMTP 发信能力。Cloudflare 当前也提供 Workers/API 等发送能力，但这仍不等同于开箱即用的完整个人邮箱；需要正确处理验证、SPF、DKIM、DMARC、退信和发信信誉。

若需要日常稳定收发，应选正规邮件服务，再严格按服务商提供的 MX/TXT/CNAME 记录配置。配置邮件路由时，Cloudflare 可能要求调整现有 MX 记录，已有邮箱用户必须先评估，避免收件中断。

19.2 更可能的误报原因

  1. 共享免费后缀的信誉会互相影响。 kdns.fr 提供者公开承认任何人都能申领名称，少数用户可能用于钓鱼、恶意软件或诈骗。部分手机浏览器、微信、QQ 或运营商的信誉系统可能粗粒度处罚整个后缀，而没有准确隔离每个子域。
  2. 页面行为很像钓鱼页。 当前 portal.js 会生成全屏“ACCESS CODE / VERIFYING / ACCESS GRANTED”界面，同时网站包含二维码、动态脚本和多个第三方资源。即使代码没有上传密码，这种视觉组合也可能触发启发式模型。
  3. 所谓密码写在公开 JavaScript 中。 password: "123456" 对真正的隐私没有保护作用，任何人打开开发者工具都能看到。静态前端无法安全保存秘密。
  4. 身份信息不一致。 页面 canonical 和 Open Graph 曾指向 whale.github.io，而访客打开的是 sore.kdns.fr，扫描器可能认为它是复制或镜像网站。
  5. 第三方供应链较多。 jsDelivr、jQuery CDN、百度静态资源、Google Fonts、图床等任一资源被阻断、被污染或信誉异常，都会影响最终页面。Cloudflare 的合法检测脚本也会使页面结构与 GitHub 仓库原始 HTML 不完全相同。

19.3 最有效的定位实验

按一次只改一个变量的方式测试：

  1. 在同一部手机、同一网络分别打开 https://whale.github.io 和 https://sore.kdns.fr。
  2. 分别用 Chrome、Edge、系统浏览器、微信和 QQ 打开，记录到底是谁弹出警告。
  3. 截图保留警告全文、网址、浏览器名称和时间。不同厂商的申诉入口完全不同。
  4. 临时把首页替换成只有标题和一段文字的纯 HTML。如果仍警告，域名/后缀信誉是首要嫌疑；如果不再警告，再逐项恢复脚本。
  5. 首先移除或改造 portal.js 的假密码门，不展示付款二维码，也不使用“验证通过/拒绝”等登录式措辞。
  6. 在 Cloudflare 暂时关闭 Bot Fight Mode 或相关 JavaScript Detections，清缓存后对照测试。该动作是定位变量，不代表 Cloudflare 脚本本身恶意。
  7. 修正 Hexo 的 url、canonical 和 og:url，重新部署。
  8. 手机端清除该网站的缓存、Cookie 和 Service Worker 后重试。
  9. 将关键 JS/CSS 自托管；必须用 CDN 时固定版本并尽可能使用 SRI 完整性校验。
  10. 确认误报厂商后，从其官方入口提交复核。Google 可通过 Safe Browsing 误报页面申诉，Microsoft 可通过 SmartScreen 反馈，国内应用需按警告页中的“申诉/反馈”入口处理。

长期公开使用时，购买自己独占、可续费和可转移的常规域名，通常比不断修补共享免费后缀的信誉问题更省时间。即使换域名，也应保留最小化第三方脚本、真实一致的站点身份和清晰内容。
